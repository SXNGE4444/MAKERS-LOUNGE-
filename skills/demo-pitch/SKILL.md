# Skill — Demo / Pitch Readiness

## Trigger
Use whenever a feature changes the core user journey, when preparing slides, and during final hackathon submission.

## Goal
Make the product understandable and demonstrable even if the judges have never seen the code.

## Demo spine
1. Problem — one concrete user pain.
2. Stakes — why it matters now.
3. Product — what the team built.
4. Live path — one primary workflow with minimal navigation.
5. Proof — result, metric, data or technical capability.
6. Architecture — only what strengthens credibility.
7. Team — who built what.
8. Next step — what becomes possible after the hackathon.

## Demo safety
Maintain:
- one production/demo URL or known local run command;
- seeded/demo-safe data when appropriate;
- backup screenshots or a short recording;
- exact credentials only in secure team channels, never in the repo;
- a fallback path if one external dependency fails.

## Presenter checklist
Lathithaa owns the demo narrative by default, but every teammate must know their 20–30 second technical explanation. Rehearse handoffs, not only individual speaking parts.

## Cut rule
If a feature is hard to explain in the pitch and does not strengthen the judged outcome, it is a candidate for removal from the demo even if it remains in code.
